# eos-pmd API (NestJS)

The data + auth backend for the Next.js app in the parent directory. Everything
the app used to do against MongoDB directly (via Mongoose in `src/lib`) now runs
here; the Next.js app talks to this service over HTTP.

## Why

Server components and server actions were opening Mongoose queries on every
request. This service owns the database connection (one pool), the permission
checks, the scoring logic and auth, and exposes a small REST surface under
`/api`.

## Run

```bash
cd api
cp .env.example .env   # fill in MONGODB_URI + AUTH_SECRET (same values as the app)
npm install
npm run dev            # watch mode on http://localhost:4000/api
```

`AUTH_SECRET` **must** match the Next.js app's — the API verifies the same
session JWT the app issues. The app points at the API via `API_BASE_URL`
(default `http://localhost:4000/api`).

Run the API before `npm run dev` in the app.

## Deploy (Render)

The repo-root [`render.yaml`](../render.yaml) Blueprint deploys this service as `eos-pmd-api`:

- **Root Directory** `api`, build `npm install --include=dev && npm run build` (the `--include=dev` is
  needed — `nest build` uses the `@nestjs/cli` devDependency), start `npm run start:prod`.
- **Health check** `/api/health`.
- **Env vars**: `AUTH_SECRET` is generated by the Blueprint and shared with the web service;
  `MONGODB_URI` you set by hand. `PORT` is injected by Render and honored by `main.ts`
  (`app.listen(port, "0.0.0.0")`).
- The cluster must allow Render's outbound IPs (or `0.0.0.0/0`) in Atlas Network Access.

Nothing browser-facing calls this API directly, so CORS stays off in production (leave `CORS_ORIGINS`
unset). The service is still publicly reachable — every route is JWT-guarded, but the `@Public()`
sign-in endpoints have no rate limiting yet.

## Layout

| Path | Purpose |
| --- | --- |
| `src/schemas/schemas.ts` | Mongoose schemas, ported verbatim from `src/lib/models.ts`. Same collections. |
| `src/common/` | Ported pure logic: `types`, `constants`, `scoring`, `attributes`, `permissions`, `richtext`, plus the `serialize*` helpers, the JWT `session` helpers, and the global `JwtAuthGuard`. |
| `src/auth/` | One-time email codes, sign-in, invitation acceptance. Returns signed JWTs; the app sets the cookie. |
| `src/projects/` | Project reads (`data.ts` equivalents) + all project/people/completion/capstone/publish mutations (`actions.ts` equivalents). |
| `src/milestones/` | Milestone reads + milestone/rating mutations. |
| `src/invitations/` | Invitation lookup + acceptance. |
| `src/activity/` | Activity log write + recent-activity read. |

## Auth

Every route is guarded by `JwtAuthGuard` (registered globally) unless marked
`@Public()`. The Next.js app forwards the `eos_session` cookie value as
`Authorization: Bearer <token>`. `@Roles('admin')` adds a role check.

## Notes

- The seed/migration scripts in `../scripts` still use `../src/lib/models.ts`
  and `../src/lib/mongoose.ts` directly — those two files are kept for offline
  DB tasks only; the app runtime no longer imports them.
- No request validation library is wired in yet; controllers accept plain JSON
  bodies and the services do the same key-by-key parsing the old server actions
  did.
